## 1. 競技・機体要件(千葉大学ロボットコンテスト2026)

- フィールド: 3376 × 5638 mm
- スタートゾーン: 1600 × 800 mm(俯瞰図の800×600mm表示と不整合があり主催確認事項)
- 壁: 規則3.2節は幅38mm・高さ100mmと明記。俯瞰図の木枠は33mm。**この33mm/38mmの矛盾は
  未解決のQ&A(Q9)として主催者側に残っている**
- ノーツ: 各チーム6個、直径約150mm、質量200g。スラローム内保持上限2個
- ビンゴ: 3×3。下段10点/中段20点/上段40点。中・上段は同列下段にノーツがある場合のみ投入可
- コンボ: 自チーム色の縦3個または斜め3個
- 勝敗優先順位: Vゴール時刻 → 得点 → ゴール回数
- 試合時間: 5分(300秒)。現行のシミュレーション試験は30〜180秒で運用中で、実競技時間に
  近づけるには延伸が必要
- 初期機体寸法: 600×600×800mm以内、展開後900mm立方以内
- 壁側面への強い接触は強制リトライにつながるため、接触を走行戦略に使わない方針

出典: `robocon2026_autonomy_plan.md`, `docs/rule/千葉大学ロボットコンテスト 2026.pdf`

## 2. 自己位置推定 要件(現行, 2026-07-27時点で有効)

自己位置推定(`lio_localization`)の受入条件は、次の2条件を**同時に**満たすこと。

- 定常位置誤差 RMSE: **10 mm以下**
- 最大位置誤差: **10 mm以下**

適用範囲: `lio_localization_sim`の評価器、Stage 4 sweepの判定、現行の設計計画。

過去の測定記録(20mm基準時点のもの)は証跡としてそのまま残し、新基準での再判定は
各runの`diag_raw_errors.csv`が存在する場合のみ、その最大値を10mmと比較して行う。
CSVのない過去runは新基準では未検証として扱う。

## 3. 破綻耐性要件(Stage 3基準、現行)

通常の精度基準(§2)とは別に、運動限界突破・センサ異常に対する要件を設ける。

- 合格基準: **破綻検知 + 自己復帰**(破綻中の位置精度そのものは不問)
- 例外: **IMU途絶**は自己復帰を狙わず、**検知してfail-safe停止**(永続発散・NaNを
  起こさないこと)を合格とする(2026-07-22変更、上記変更履歴参照)

| シナリオ | 合格基準 | 現状 |
|---|---|---|
| 運動限界突破(速度・加速度・角速度・角加速度) | 透過(推定器の限界ではないため精度要件のまま) | PASS |
| 壁への接触(0.37m食い込み) | 透過 | PASS |
| IMUノイズ50倍 | 透過 | PASS |
| LiDAR途絶(10秒) | 検知+自己復帰 | PASS(復帰は途絶中ドリフト依存の確率的挙動、既知の制約) |
| LiDAR外れ値(10秒) | 検知+自己復帰 | PASS |
| IMU途絶(0.5秒/10秒) | 検知+fail-safe停止 | PASS(2026-07-22修正後) |

出典: `01_icp_outlier_investigation.md` 追記11・11-2・11-3

### 3.1 目標の明確化(2026-07-28)

本プロジェクトの目標は、千葉大学ロボットコンテスト2026の要件を満たすことだけではなく、
**より汎用的な「ロボコン向け自己位置推定」を構築すること**である。その一環として、
「衝突を避けること」自体は目標ではなく、**どんな状況でも(衝突時・フィールド破壊時を
含む)、自己位置推定が正確な値を出し続けるか、それが無理なら安全にエラーを示せること**
を要件とする。

Stage 1〜3(解析的シミュレータ)では壁への接触(0.37m食い込み)を「透過(頑健)」で
PASSしているが(§3表)、これは解析的シミュレータ上の理想化された接触モデルでの結果に
とどまる。Unity側の物理演算・衝突判定を伴うStage 4では、まだ同等の検証をしていない。

### 3.2 汎用性の追加軸: 坂(非平坦フィールド)への対応(2026-07-28)

千葉大学ロボットコンテスト2026自体のフィールドには坂(傾斜)の規定はない
(ルールブック確認済み、フィールドは全ゾーン平面)。**しかし近年のロボコンでは坂を
採用するフィールドが増えてきている**ため、このプロジェクトを「今回の競技専用」ではなく
「他のロボコンにも通用する汎用自己位置推定」として作るなら、非平坦フィールド(坂)への
対応も設計スコープに含める、というのがユーザーの意図である。これは§3.1の
「衝突・フィールド破壊への耐性」とは別の軸(フィールド形状の汎用性)であり、両方を
満たすことが「汎用的なロボコン向け自己位置推定」の要件となる。

**この一般化により、§3のIMU途絶に対する現行方針「検知してfail-safe停止(要再起動)」を
無条件には使えなくなる。** その前提は「機体が平坦な床の上で静止する」ことだったが、
坂のあるフィールドではプロセスを止めて機体を無制御のまま放置すると、重力で滑落・転倒
しうる。**坂を含む汎用フィールドを前提にするなら、プロセス(推定・制御)を完全に
停止させてはならない。**

これは§3のIMU途絶時方針(2026-07-22決定、「復帰を狙わずfail-safe停止」)と直接矛盾する
ため、既存方針の単純な再確認では済まない。少なくとも次の設計判断が必要:

- 「止めない」が具体的に何を指すか: 制御ループ自体は動かし続け、機体をその場で
  安全に保持する(能動的なホールド)ことを指すのか、それとも推定ノードのプロセス
  (ROSノード)自体をkillしない(クラッシュさせない)ことだけを指すのか
- IMU途絶中に能動的にホールドし続ける場合、途絶前の推定を使い続けるのか、
  傾斜センサ(IMUの重力方向成分)だけは生かして最低限の姿勢制御を続けるのか
- 現行のLiDARマッチング(`laser_scan_matching_node`)は水平な2Dスキャン平面を前提にした
  planar ICPである。2026-07-23に判明した「スキャン平面が壁の上端より上/下にあるかで
  壁が見える/見えないが決まる」問題(`04_stage4_resume_notes.md`§1)と同種の理由で、
  機体が傾くとスキャン平面ごと傾き、壁の見え方が変わる/消える可能性がある。坂対応は
  IMU/バックエンドの3D姿勢推定(GTSAMは元々3D)だけでなく、LiDAR側の前提も再検討が要る

**千葉大学ロボットコンテスト2026自体には坂がないため、今回の競技向けの検証としては
優先度は高くない。** 「汎用ロボコン向け自己位置推定」という将来目標のための設計課題
として記録し、今回の要件(§2・§3)とは切り分けて扱う。

なお、機体自体がバラバラになるケースは、次のルール6.7「破壊」により即座に競技除外
されるため、その状態の位置推定まで設計する必要はない。

> 「ロボットが複数の部分に分離したとき、そのロボットは破壊したとみなす。破壊した
> ロボットは、直ちに競技から除外される。」

設計対象は「機体は分離していないが、衝突・フィールド破壊によって姿勢が傾く/
不測のデブリに乗り上げる可能性がある」状況に限定できる。

§6「残る課題」の1項目「接触しない走行制御・経路を先に保証し、測位誤差と衝突応答を
分離する」は、**測定条件を切り分けるための実験手法**であり、「衝突を避ければよい」
という製品要件への読み替えではない。切り分けが済んだ後は、Stage 4で衝突・
フィールド破壊が実際に起きた場合にも、本節冒頭の要件(正確な推定継続、または
fail-safeなエラー提示)を満たすことを改めて検証する必要がある。

### 3.3 ノーツ衝突は最終的に有効化する(2026-07-28)

2026-07-27の検証で、Unity側の「ローカライゼーション基準シーン」はノーツを物理剛体の
まま残しつつ**接触力だけを無効化**していた(ロボットが往復走行のたびに必ずノーツへ
接触し、測位精度検証にとってノイズになっていたため)。これはCodexが導入した
**あくまで測位精度切り分けのための暫定簡略化**であり、最終仕様ではない。

**最終的にはノーツの接触力を再度有効化し、ロボットがノーツを押す・弾く・位置を
変えることを許容した上で、自己位置推定が正確であり続けることを目標とする。**
これは§3.1の「衝突・フィールド破壊時も推定を継続する」という一般目標の具体例の一つで、
実際の競技ではノーツ回収・運搬のたびにノーツへ接触・移動させることが正規の動作
だからである(衝突ではなく通常のゲームプレイ)。

**既存の技術的土台**: `laser_scan_matching_node`には既に、既知の壁マップに含まれない
物体(ノーツ含む)をICPから除外する2パスICP機構がある(`planar_exclude_balls`,
`ball_exclusion_distance`, `ball_exclusion_max_extent`。空間的な広がりでクラスタ判定、
半径フィットより頑健。詳細は`04_stage4_resume_notes.md`§11)。この仕組みは「ノーツは
未マップの可動物体」という前提を既に組み込んでいるため、方向性としては正しい。
**ただし、ノーツの接触力を有効化した状態(ノーツが実際に押されて動く状態)での
検証はまだ行っていない。** 除外ロジックがノーツの移動前後どちらの位置でも
同様に機能するか、移動中のノーツをLiDARが捉えた場合に誤って壁側点群として
取り込んでしまわないか、を次のUnity検証で確認する必要がある。

## 4. Unity移行時のシミュレーション精度合格条件

- JSON寸法とColliderの差: 1mm以下
- 無負荷直進・横移動・旋回の速度誤差: 5%以下
- 走行軌跡の実機との差: 50mm以下から開始し、最終10mm以下
- 球投入100回の成功率: 95%以上
- 同一初期条件での試験結果を記録し、Unity/実機双方の分布で比較する

摩擦係数・オムニローラ特性はルールPDFから得られないため現在値は仮値。「正確な
シミュレーション」の完成には実機の質量・重心・慣性、床・車輪摩擦、モータ特性の実測が必須。

出典: `unity6_simulation_plan.md`

## 5. 開発ステージゲート

1. フィールド検証: 全寸法誤差5mm以内、全衝突形状を確認
2. 三輪オムニ基盤: 指令追従誤差5%、壁無接触で完走
3. 競技用既知マップ: 走行中RMSE 10mm以下・最大位置誤差10mm以下(現行はここに相当し未達)
4. 機構物理モデル: 回収・保持・投入を各100回、成功率95%以上
5. ルール状態機械: 2球制約・下→中→上投入順を全テストで遵守
6. 固定戦略完走: 既知位置の3球で縦コンボを10回連続達成
7. 時間最適化: 軌道・加減速・機構並行動作を最適化
8. 自己判断: ずれ・失敗・経路閉塞・相手機体に対して再計画し90%以上完走
9. ドメインランダム化: 摩擦・質量・遅延・ノイズを実測範囲で振り100試合95%以上完走
10. 実機移行: 同一ROSインターフェースでHardware-in-the-loop、段階的速度解放

速度を先に上げると接触・認識・機構失敗が混ざって原因を分離できないため、各段階で
成功率を固定してから次へ進む方針。

出典: `robocon2026_autonomy_plan.md` §5

## 6. 現在地のまとめ

- ステージゲート3(自己位置推定 10mm)は**RMSE達成・最大誤差未達**で保留中
- 最大10mmを正式受入にするために最低限必要な項目(2026-07-27検証レポートより):

     (**測定手法として**衝突と無縁の条件で切り分けるという意味。衝突自体への
     頑健性を諦めるという意味ではない。§3.1参照)

  3. WSL/Unityブリッジのスケジューラ変動を実機Linuxまたは専用シミュレーション実行環境と比較する

- 上記の切り分けが済んだ後、**Stage 4で衝突・フィールド破壊時の推定継続/fail-safe
  挙動を明示的に検証する項目を追加する必要がある**(§3.1、現時点で未着手)。
