2026-07-21時点のlio_localization(2D LIO-SAM方式)の状況:

**ブレークスルー**: 長年の残課題だった最大ドリフト散発スパイクとスピンバースト・ヨーロックの根本原因を特定・修正した。犯人は②(ICP/デスキュー)ではなく**③のIMU積分の時間管理3欠陥**(①ノードラベル時刻と積分区間終端の+20ms不一致、②ノード境界ごとのdt=0.001固定仮定による積分時間欠損、③IMU到着レースによる短すぎるCombinedImuFactor+DCS誤帰属)。詳細はdocs/icp_outlier_investigation.md 追記5。

**到達性能**(180秒フル×3、2026-07-22最終): 定常RMSE **1.01〜1.04mm**、最大ドリフト**3.87/4.36/5.15mm**、ヨーRMSE 0.09〜0.17°、リセット0。**3/3完全PASS(要件RMSE≤10mm/max≤20mmを桁違いに達成)**。意図的CPU負荷(slow=397〜640、通常の数十倍)でもmax 4.3〜6.0mm維持。③融合の実力(真値からmax 3.8mm)に/odom_fastがほぼ追いついた状態。

**追記9(2026-07-22)の決定打**: 残っていた並進過渡(10〜88mm)の真因は③でなく①のスタンプ不整合だった。①の姿勢は正確(pose-time基準で真値から1.5mm)だが、propagatorのdeltaTijとIMUスタンプ間隔が負荷時に最大34ms乖離するのに後者でスタンプ→ズレ×速度が見かけ誤差に。修正: `confirmed_time_+deltaTij`でスタンプ(self-consistent)。単調性クランプは誤差再注入で悪化し撤回(非単調2%・最大28msは②が許容)。③側もintegrate_imu_up_toにゼロ次ホールド端数詰め追加(ノード間隔と積分区間のズレ109→0件)。

**センサは律速でない**(追記7): 全センサ理想化(LiDAR/IMUノイズ・バイアス全ゼロ)でも数字が変わらない。よって観測側の改善策(点対点ICPへの切替、decimation=1、tikhonov調整、高性能LiDAR)は全て原理的に効果ゼロ。点対点ICPは3経路(精度・速度によるスキャン飢餓・収束品質)とも実測で棄却済み。

**evaluatorの計測バグを本セッションで3件修正**: ①タイムスタンプ不整合、②真値の最近傍マッチ→線形補間、③真値未着時に「最後に届いた真値」と比較(追記8、これが最大。max 13.4→9.08mmへ)。いずれも長く「推定器の性能問題」として扱われていた。**物理的にありえない出力(1msで38mm=38m/s)を見たら、まず計測系を疑うこと。**

**ブランチ状態**: lio_localization `feature/icp-covariance`(追記4のCensi型共分散伝播[保守的クランプ付き、wall_use_icp_covarianceで無効化可]+③の3修正。mainは未変更)。lio_localization_sim `feature/eval-fidelity`(evaluator真値線形補間+スピン窓3秒シフト修正。masterは未変更)。ワークスペースは両ブランチをビルド済み。

**高速診断フレームワーク常設**: `include/lio_localization/diag_recorder.hpp`(ヘッダオンリー、テンプレート)。ホットパスはメモリpushのみ、終了時一括dump、パラメータ空で無効化。付け外し式ファイルI/O診断の汚染問題(追記5)への恒久対策。Sonnet敵対的レビューでmutex保護・on_shutdownハンドル解除・満杯/失敗ログ・例外安全化済み。①に`diag_odom_path`で/odom_fast 1kHz全記録を配線済み。実機使用可。**次に診断が要るときはこれを使う**(付け外し不要)。lpf_tuneやσ等の実験はyaml上書きで(コード既定は不変)。

**第三段階 破綻シナリオ耐久(追記11、2026-07-22)**: 合格基準=破綻検知+自己復帰。7中5 PASS。限界突破(v8/a22/ω8/α60)・壁衝突(0.37m食い込み)・IMUノイズ×50 は透過(推定器に影響せず頑健、max<10mm)。LiDAR途絶/外れ値10s は検知+11〜14sで完全復帰。**IMU途絶ギャップは修正済み(追記11-2)**: ①③両方にIMUライブネスwatchdog(steady_clock、0.3秒超でラッチ、20Hz)。③=スキャン処理停止でグラフ凍結、①=/odom_fast配信停止。ユーザー判断で「IMU喪失=即破綻、復帰は狙わず検知して停止(fail-safe halt)、NaN発散だけは防ぐ」。検証: 途絶0.5/10秒とも検知+停止・NaN消滅、正常+高負荷(slow=71)で誤発火ゼロ。ラッチ後は要再起動。**LiDAR途絶の復帰は確率的**(途絶中ドリフトがICP再捕捉半径2m超で復帰不可、追記11-3。検知は常時機能)。シナリオ生成: trajectory.py pattern 2000番台(時間ワープ/振幅膨張)、imu_sim/lidar_sim の fault params、docs/session_results/run_stage3.sh・analyze_s3.py。

**残課題(優先度低)**: (1) ①スタンプの非単調性(2%・最大28ms)の根治=①のdeltaTij積算(再積分の端数)是正、③のZOHと同型の対処。(2) diag_recorderのungraceful終了(kill・電源断)でメモリデータ消失(長時間走行なら中間flush/容量拡大)。(3) LPFトレードオフ: tau=0はノイズ増幅40mm、既定0.005が最適点付近(追記6/9)。バースト開始の残留ヨージャンプ1.4〜1.7°はlpf_tau=5ms×ω由来。

**実機はデスクトップLinux予定**。ジッタは消せないので「ジッタ耐性」で解く方針(追記5の3欠陥修正がまさにそれで、環境に触れずRMSE 4.3→1.6mm)。環境側の施策は sudo不要=taskset でコアピン留め、sudo必要=rtprio設定でSCHED_FIFO・CPUガバナperformance(ユーザーに依頼すること)。

**未検証の弱点(IMUカバレッジ待ちの導入で生じた、2026-07-21時点で一度も発動せず未テスト)**: (a) IMU途絶から復帰した瞬間、保留していた最大40件を`drain_pending_results()`が一気に連続処理し、ISAM2 update×40で200〜800msブロックしうる(1周期あたりの処理件数制限なし)。これは「処理停滞→補正断絶」という既知の失敗モードそのもの。(b) `update_lidar_dropout_diagnostics()`が`process_scan_result()`内にあるため、待機し続けると途絶診断が一度も走らず、信頼性喪失検出・リセットが沈黙する(出るのは保留溢れ警告のみ)。対策案は「drain件数制限」と「待機中も途絶診断を回す」。故意にIMUを数百ms止める試験を入れるべき。

**σ調整の結論(2026-07-21、追記6)**: `wall_prior_base_yaw_sigma`を0.3→0.01(30倍)まで締めても発散・リセット・DCS発火ゼロ。追記3の「Censi型は原理的に過信傾向」は誤りで、真因は欠陥1の7.4°系統ズレとの組み合わせだった。ただし効果もゼロ(pos平均1.55mm vs 1.54mm)。理由は**残る>15mmイベントがほぼ全てヨー誤差0.01〜0.06°の純並進現象**だから。既定0.3のまま据え置き(実機での系統誤差マージン)。次に着手するなら並進側(ホストジッタ由来、0.2〜1.4秒の過渡、バースト無関係)。**検証時の罠**: 「>12mm区間の数」はσではなくslow smoother回数とほぼ線形＝実質ホスト負荷計。WSL2ではrun間比較の前に負荷を揃えるか、中央値・平均など負荷に強い統計量を使うこと。

**σ(壁priorの信頼度)の4層構造**: 層1=N数ヒューリスティック(base_xy 0.03/√N_x≈1.34mm、base_yaw 0.3/√N≈0.77°、縮退時は1.0m/1.0rad)、層2=Censi型ICP共分散(実測σ_yaw 0.033°・σ_x/y 2.0〜2.4mm。層1をフロアに緩める方向のみクランプ)、層3=DCS(物理妥当性ゲート超過分だけ連続膨張)、層4=Huber(k=1.345、残差に応じ重み減衰)。層2のyawは層1より23倍タイトで、これは追記3が生σで発散した「1/26まで過信化」と整合(クランプが正しく防いでいる)。
