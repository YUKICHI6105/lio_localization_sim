# ベースコードがある開発のオーケストレーション

このSkillは、信頼できる参照実装(研究室の手書きスクリプト、旧バージョン、移植元コード等)を土台にした開発を、メインエージェント+サブエージェント体制でどう進めるかの運用手順である。`/orchestration-with-base`で明示的に呼び出す。基本のモデル配分方針は`orchestration-greenfield`と共通なので、ここではベースコードがある場合特有の注意点に絞る。

## モデル配分の基本方針(共通)

| 局面 | モデル |
|---|---|
| 日常のメイン進行 | Sonnet |
| ベースコードとの忠実性比較・整合性判断 | Fable/Opus(1回のフォアグラウンド委譲) |
| 定型的な移植・実装 | Sonnet |
| 難所(挙動が食い違う原因の特定) | Fable/Opus(発生時エスカレーション) |
| テスト実行等の定型検証 | Haiku |

`Agent`呼び出し時は`model`を必ず明示する。

## ベースコード特有の落とし穴

### 1. 「本当に信頼できるベース」を最初に特定する

- リポジトリに複数の参考資産(研究室で長年使われてきた手書きスクリプト、AIやツールが生成した未検証のドラフト、途中で放棄された旧実装など)が混在している場合、どれが「実機で検証済みの正しい挙動」でどれが「生成途中の信頼できないコード」かを**最初にユーザーに確認する**。この見極めを誤ると、間違ったコードを正として移植してしまう。
- 迷ったら質問すること。「既存資産」とひとまとめにして扱わない。

### 2. 差分は三分類で報告する

新実装をベースコードと比較する際は、差分を必ず次の3種類に分類してユーザーに報告する:

1. **一致**: 実質的に同じ挙動。
2. **意図的な改良**: ベースにない安全対策・堅牢化・命名整理などで、こちらの判断で加えた変更。
3. **要確認のぶれ**: ベースと異なるが、改良とも言い切れない差異。単位系の違い・タイムアウト値・コマンドの表記揺れなど。

「要確認のぶれ」は**コードを修正せず報告に留め**、ユーザーの判断を仰ぐ。改良か劣化か自明でない変更を、良かれと思って黙って直さない。

### 3. ベースコードの欠陥・デッドコードをそのまま持ち込まない

- ベースコードに未検証の危険な省略(例: 安全装置の未設定)があれば、それは「一致」させるべき対象ではなく、改良の候補として明示的に提案する。
- 逆に、新実装側で追加したが元に存在しない要素(未使用の引数、デッドコード分岐)は、ベースとの忠実性を優先するなら削除を検討する。

### 4. 参照済みの旧ドラフトを消す時は、参照ごと消す

- 信頼できないドラフトコードを削除する場合、そのドラフトへの言及(docstring・設計文書・コメント)がリポジトリ内に残っていないか`grep`で全体を確認する。
- 「削除済み」という注記だけを残すのではなく、**最初から存在しなかった体裁**に書き換える(出典が必要なら実在する信頼できるベースへ差し替える)。中途半端な注記は将来読む人を混乱させる。

### 5. 比較評価の委譲プロンプトには「本当のベース」を明示する

- Fable/Opusへの比較評価を委譲する際は、「どのファイルが信頼できる参照実装か」をプロンプトに明記する(自動判定させない)。判定を誤らせないため。
- 比較対象のコマンド列・数値・単位系など、具体的な照合ポイントをプロンプト側であらかじめリストアップしておくと、抜け漏れが減る。

## 手順の流れ

1. ユーザーに「本当に信頼できるベースはどれか」を確認する(複数候補がある場合は特に)。
2. Fable/Opusへ一度、比較評価タスクを委譲する(コード修正はさせず、三分類レポートのみ作らせる)。
3. レポートをユーザーに提示し、「要確認のぶれ」ごとに対応方針(ベースに合わせる/このまま/別の値にする)を確認する。
4. 確定した方針をSonnet(メインまたはサブエージェント)で実装する。
5. 不要になった旧ドラフトを削除する場合は、参照除去を別タスクとして明示的に行う(消し忘れが起きやすい)。

## やってはいけないこと

- 複数の参考資産を「既存資産」と一括りにして、信頼度を確認せずに移植元として使う。
- ベースとの差分を「改良」と「ぶれ」の区別なく一括りに報告・修正する。
- ドラフト削除時に、ドキュメント上の参照を消し忘れる。
