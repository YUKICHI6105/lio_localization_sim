# ゼロから作る新規開発のオーケストレーション

このSkillは、参照実装(移植元・ベースコード)が存在しない新規開発を、メインエージェント+サブエージェント体制でどう進めるかの運用手順である。`/orchestration-greenfield`で明示的に呼び出す。

## 前提となる失敗パターン

- メインエージェントを終始上位モデル(Fable/Opus)にして、実質「サブエージェントへの中継役」しかしていない状態は、上位モデルの無駄遣いになる。
- 逆に、要件の曖昧さや設計判断をメインエージェント(Sonnet)任せにすると、実装が進んでから手戻りが起きる。
- どちらも「タスクの性質」でモデルを選ばず「セッション全体」で固定してしまうことが原因。

## モデル配分の基本方針

| 局面 | モデル | 呼び出し方 |
|---|---|---|
| 日常のメイン進行(会話・分配・軽微な実装) | Sonnet | セッションのメインモデルとして常時 |
| 要件確認・設計計画の立案 | Fable/Opus | `Agent`ツールを`model`明示・`run_in_background: false`で1回だけフォアグラウンド呼び出し |
| 定型的な実装(パターン踏襲・機械的に多いだけ) | Sonnet | サブエージェントに委譲 or メインが直接編集 |
| 判断が要る難所(バグ根本原因、アーキテクチャ上の矛盾) | Fable/Opus | 発生時にエスカレーション(常駐させない) |
| テスト実行・ログ抽出等の定型検証 | Haiku | 失敗時のみSonnet以上へエスカレーション |

`Agent`ツールの`model`パラメータは**必ず明示する**。省略すると呼び出し元(メイン)のモデルを継承し、メインが上位モデルの場合は全サブエージェントが無駄に上位モデルになる。

## 手順

### 1. 要件の確認と実装計画の立案(Fable/Opusへ一度だけ委譲)

- ユーザーの要求・既存の要件定義書等を渡し、**曖昧な論点のリスト**と**実装計画(ファイル単位のタスク分割案)**を成果物として作らせる。
- **このサブエージェントにAskUserQuestionを呼ばせない。** サブエージェントはユーザーと直接対話できない(バックグラウンドで1往復して結果を返すだけの設計)ため、論点リストは一度メインに返させる。
- メイン(Sonnet)がそのリストを受けて`AskUserQuestion`でユーザーに確認する。
- ユーザーの回答を、**同じサブエージェントに`SendMessage`で送り返す**(名前/agentId指定)。これにより要件文書・コードベースの読み込みをやり直さずに、回答を踏まえた最終計画に更新できる。
  - 注意: このAgent呼び出しを`run_in_background: false`(フォアグラウンド)で行った場合、完了後の`SendMessage`による再開が失敗することがある(ディスク上にトランスクリプトはあるのに「見つからない」と返る事例を確認済み)。再開を前提にする場合は、その回だけでも`run_in_background`をデフォルト(バックグラウンド)にするか、再開できなかった場合は新規Agent呼び出しで要件要約を渡し直す想定をしておく。

### 2. タスク分割はアーキテクチャの境界に沿わせる

- レイヤー(View/ViewModel/Model等)や機能単位など、**並行実装しても互いに干渉しない境界**でタスクを切る。
- 各タスクのサブエージェント委譲プロンプトには、関連ファイルパス・既存の命名規則・依存する型やインターフェースを具体的に書く。「計画を踏まえて実装して」のような丸投げをしない。
- 委譲は「複数の側面がある」「入念にやりたい」程度では正当化しない。1〜数ファイルの変更で仕様が明確なら、メインが自分でRead/Editする方が速く、文脈の再導出コストもかからない。

### 3. 検証は階層化する

- 通常のテスト実行・ログ抽出はHaikuに任せて件数と成否だけ報告させる。
- テストが落ちた・クラッシュした場合は、その原因究明はメイン(Sonnet)かFable/Opusにエスカレーションする。サブエージェントの「全部パスしました」という報告を鵜呑みにせず、疑わしい変更(ライフサイクル管理、並行処理、GUIイベントループ絡み等)は自分でも実行して確認する。
- 原因を自分(メイン)で特定できた場合は、そのまま自分で修正する。「診断はしたが修正は別のサブエージェントに投げる」は無駄な往復になる。

### 4. 委譲プロンプトの書き方チェックリスト

- 背景(何のためにこの変更をするか)を書く。
- 既存のファイルパス・関数名・行番号など、実際に調べた具体情報を書く(サブエージェントは何も知らない前提)。
- 制約(言語バージョン、既存のアーキテクチャ方針、変更してはいけない箇所)を明記する。
- 検証手順(テストコマンド、確認すべき挙動)を具体的に指定する。
- 期待する報告形式(変更ファイル一覧・テスト結果件数など)を指定する。

## やってはいけないこと

- メインを終始上位モデルにして、実装・検証・デバッグの全てを機械的にサブエージェントへ回す(中継役に徹してしまう)。
- サブエージェントにAskUserQuestionを呼ばせて、ユーザーとの対話を代行させようとする。
- 委譲時に`model`を省略する。
- サブエージェントの完了報告(テスト全件パス等)を検証せずに次の作業へ進む。
