# 実験履歴: 減速時位置誤差スパイクの原因調査(2026-07-28)

- 実行環境: Unity Editor + ROS 2 フルスタック(closed-loop、`07_stage4_unity_production_summary.md`と同構成)。
- 対象期間: 2026-07-28。
- 生データ: `docs/stage4_runs/<run名>/`。
- 関連ドキュメント: [`backend_estimator_architecture_2026-07-28.md`](../requirements/backend_estimator_architecture_2026-07-28.md)(因子グラフ構造・知覚の詳細図)、
  `06_localization_10mm_validation_report_2026-07-27.md`(前日までの経緯)。

2026-07-27時点で残っていた「最大位置誤差10mm以下」未達(§4.5参照)について、Unity側に
IMUバイアスの真の連続時間ランダムウォークを導入した上でRepeatLaps(往復走行)を有効化し、
60秒評価窓を最大限使う構成でベンチマークを継続した。本レポートはその過程で発見した
**往復走行の折り返し(減速→方向転換)に伴う位置誤差スパイク**の原因調査記録。

## 1. バイアスランダムウォーク導入後の再現性確認

Unity側に`biasRandomWalkSigma=0.0001`の真のランダムウォークを実装し、3回連続実行して
再現性を確認した。

| run | 位置誤差 mean/RMSE/max | 判定 |
|---|---|---|
| bias_random_walk_20260728 | 6.28 / 6.91 / 12.90mm | 定常PASS / 最大FAIL |
| bias_random_walk_rep2_20260728 | 6.06 / 6.59 / 13.07mm | 定常PASS / 最大FAIL |
| bias_random_walk_rep3_20260728 | 6.14 / 6.83 / 12.99mm | 定常PASS / 最大FAIL |

3回とも同water水準(RMSE 6.6〜6.9mm、max 13mm前後)で安定してmax FAIL。スパイクの
**発生時刻(位相)は3回とも一致しない**が、**スパイク間隔は約8秒で3回とも一致**しており、
経路(RepeatLapsの区間長)由来の周期構造と、バイアスランダムウォークの確率的要素が
組み合わさっていることを示唆した。

## 2. 減速時スパイクの発見と切り出し

`diag_raw_errors.csv`(evaluatorの生誤差ログ)を1秒粒度で分析したところ、誤差は
全区間に一様ではなく、**8mm超のエピソードが60秒中40前後、平均継続時間0.4〜0.6秒**に
集中していることが分かった(`icp_only_diag_20260728`基準: 41エピソード、平均9.41mm、
最大14.35mm、合計占有33.5%。平常時(8mm以下)のみのRMSEは5.04mmと十分優秀)。

速度プロファイル(`accel_profile_diag_20260728`、`/odom_fast`を1kHzダンプ)とエラーの
時刻を突き合わせたところ、**誤差ピークは速度がゼロクロス(往復走行の折り返し・完全停止)
する約0.1〜0.13秒前**に発生し、速度がゼロを通過した直後に収束する、というパターンが
2回の独立したピーク(t≈25.38s, t≈59.03s)で再現した。

## 3. ICP単体 vs 融合推定の比較

`ScanMatchResult`の`wall.corrected_pose`(ICP単体の絶対観測)を真値と直接比較する
診断ノードを追加し、融合後の誤差と比較した(`icp_only_diag_20260728`)。

- 平常時: 融合4.2〜5.3mm、ICP単体7.7〜9.1mm(ICP単体は常時2倍前後ノイズが大きい)
- **誤差ピーク付近(t=24-25, 50-51, 57-59付近)**: 比(ICP単体/融合)が1.0前後まで低下し、
  複数箇所で**ICP単体の方が融合結果より精度が良い**逆転が発生

融合(IMU積分・スムーザー)が通常発揮している「ICPノイズを均す」効果が、まさにこの
瞬間だけ消えていることを確認。バイアス側の応答特性を疑う根拠となった。

## 4. Estimator側パラメータの切り分け(すべて原因ではないと確認)

| run | 変更内容 | 位置誤差 mean/RMSE/max | 備考 |
|---|---|---|---|
| lag15_ab_test_20260728 | `smoother_lag_sec` 0.5→1.5 | 6.46 / 7.15 / **14.06mm** | slow smoother警告19回(通常1-2回)に急増。悪化のみ、棄却 |
| zupt_v1_20260728 | ZUPT閾値0.1m/s導入 | 6.01 / 6.79 / 14.06mm | 8mm超エピソード時間33.5%→28.6%とわずかに改善するがmax不変 |
| zupt_v2_thresh05_20260728 | ZUPT閾値0.5m/s | 6.32 / 7.06 / **27.92mm** | **全run中最悪**。まだ動いている速度域で速度=0を強制し逆効果。棄却 |
| zupt_v3_thresh03_20260728 | ZUPT閾値0.3m/s | 6.21 / 6.91 / 14.20mm | v1と同水準、v2のような破滅的悪化は回避 |
| imu_dynamics_v1_20260728 | 高ダイナミクス検知でwall σ締め(閾値2.0m/s²) | 6.22 / 6.95 / 14.82mm | 巡航中の通常加減速(4-7m/s²)でも常時発火し局所対策になっていない。効果なし |
| relinearize_0001_20260728 | `relinearizeThreshold` 0.01→0.001 | 6.14 / 6.81 / 13.45mm | slow smoother警告11回に増加。効果なし |

ZUPT(v1〜v3)・IMU動的信頼度・`smoother_lag_sec`・`relinearizeThreshold`のいずれも、
効果なしまたは悪化のみで、現在はすべて無効化(`zupt_enabled=false`,
`imu_dynamics_enabled`は要再検証、`relinearize_threshold`は0.01に復元)。

## 5. バイアス・センサノイズの切り分け(すべて原因ではないと確認)

「原因はIMUバイアスの応答特性では」という仮説を検証するため、Unity側の注入モデルを
1項目ずつ凍結して比較した。

| run | 条件 | 位置誤差 mean/RMSE/max | ヨーRMSE | 備考 |
|---|---|---|---|---|
| (§1基準) | ランダムウォークあり(通常) | 6.1-6.3 / 6.6-6.9 / 12.9-13.1mm | 0.18-0.21° | 基準 |
| no_random_walk_test_20260728 | ランダムウォーク停止(固定バイアスのみ) | 6.34 / 7.07 / 15.98mm | 0.177° | 変化なし(むしろ悪化) |
| no_bias_test_20260728 | 固定バイアスも0(純ノイズのみ) | 6.11 / 6.77 / 13.21mm | 0.143° | 変化なし |
| noise_10x_reduced_20260728 | センサノイズ1/10(バイアス0のまま) | 5.82 / 6.79 / **16.40mm** | **0.120°(改善)** | ヨーは改善(ノイズ低減が正しく効いている証拠)、位置maxは不変〜悪化 |

バイアス(固定値・ランダムウォークいずれも)、センサノイズ(1/10に低減)いずれも
位置誤差スパイクの規模を変えなかった。ヨーRMSEはノイズ低減で明確に改善しており、
計装・変更自体は正しく機能していることも確認済み。

## 6. 生IMU値の直接調査

`raw_imu_inspect_20260728`はガウス性の白色雑音(`accelNoiseSigma`/`gyroNoiseSigma`)
のみを停止した実験で、固定バイアス(`accelBiasX=0.05, accelBiasY=-0.03,
gyroBiasZ=0.005`)とバイアスランダムウォーク(`biasRandomWalkSigma=0.0001`)は
通常運用の値のまま動いていた。`diag_raw_imu.csv`のt≧3s平均(ax=+0.0575,
ay=-0.0418, gz=+0.00426)は設定した固定バイアス値とほぼ一致する。

`/imu/data`の生値を1kHzで記録して誤差ピーク(t≈58.95s)前後を確認した結果:

- az(重力方向)9.79〜9.82m/s²で終始一定。gz(角速度)は0.003〜0.007rad/sで、設定した
  ジャイロバイアス(+0.005 rad/s)付近で安定しており、異常な回転はない。信号飽和・
  NaN・通信破損は確認されない
- ax/ayは減速→符号反転→逆方向加速という、往復走行の折り返しとして物理的に正常な挙動
- t=58.85〜59.10s窓内の局所最大は**ax≈+6.20 m/s²**で、設計上限(0.5G=4.905 m/s²)比
  ではこの1窓に限れば約26%超過。**全走行を通せば平面加速度(ax・ayの合成)の最大は
  約10.38 m/s²に達し、これは設計上限の約2.1倍(約112%超過)**であり、折り返しの
  たびに大きく超過している。t=58.95s付近だけでなく、全折り返しでの超過状況を
  対象に含めて調査する必要がある
- PD制御力自体は`Vector3.ClampMagnitude`でクランプされているが、実測加速度(速度の
  有限差分)は地面摩擦・物理ソルバーの拘束解決等の副次力を含むため、クランプの対象外
- backend側`kMaxAcceleration=4.905`(壁補正の物理妥当性ゲート計算に使用)との
  齟齬はあるが、この項は`dt²`(≈25ms)でスケールしLiDARノイズマージン(45mm)に
  埋もれるため、DCS発火・壁補正拒否ログはこのrun全体で1件も出ておらず、現状の
  実装には影響していない

NaN・信号飽和・通信破損といったセンサー故障の兆候はない。ただし設計上の運動モデル
(0.5G上限)を大きく外れた運動が実際に起きているのは事実であり、この2つは別の主張
として扱う必要がある。

## 7. 結論(2026-07-28時点)

減速直前〜直後の位置誤差スパイク(12〜16mm、要件A max≤10mmをFAIL)について、
estimator側で動かせるほぼ全パラメータ(バイアス3パターン、センサノイズ、
`smoother_lag_sec`、`relinearizeThreshold`、ZUPT、IMU動的信頼度)を検証したが、
**今回試した設定・条件下ではいずれも改善せず、主要因である可能性が下がった**
(各機構・閾値を完全に否定する試験ではない。特にIMU動的信頼度は閾値2.0m/s²が
通常走行中も頻繁に発火しており、「この実装・閾値では効果がなかった」ことが
分かるのみで、動的補正という方式自体を棄却する根拠にはならない)。生センサー値
自体にも異常はない。

知覚ノードで実際に使われている壁推定経路は、汎用3D ICP(coarse-to-fine)ではなく
**独立したplanar 2D point-to-segment solver**であり(詳細は
[`backend_estimator_architecture_2026-07-28.md`](../requirements/backend_estimator_architecture_2026-07-28.md)参照)、
全体の対応点数N(`correspondence_count`)はスキャンごとに変動する実測値で、backendの
`yaw_sigma = base/√N`はこれに基づいて正しく動的計算されている。一方、**X/Y軸別の
内訳(`x_axis_correspondence_count`等)は全体Nの単純折半、共分散値は固定
`diag(1e-5,1e-5,1e-5)`、縮退判定は常にfalse**であり、軸別のσ計算・縮退軸の緩和・
ICP共分散によるσクランプは実際のスキャン形状を反映せず動作している。これは現行
システムの論理的な弱点であり、減速時スパイクの挙動に関係している可能性がある。
また、円柱による復旧経路(連続拒否→再ローカライズ)は現行Unity設定(円柱未登録)
では機能せず、`dropout_error_sec=120秒`>評価窓60秒のため信頼性喪失の異常通知も
発火しない。

残る候補:
- **planar solverの軸別対応点数の均等割り当て・固定共分散値**(全体Nは実測だが、X/Y軸別の重み付けと縮退検出が現状機能していない)— 優先度が高い
- 壁補正(ICP)側の幾何学的性質(現時点で具体的な機序は未特定)
- Unity物理エンジンが設計加速度上限(0.5G)を超過している事実そのもの(1窓では約26%、全走行では平面加速度が最大約2.1倍=約112%超過。DCS/ゲート機構への影響は全体Nベースのσ計算自体は健全なため限定的)
- IMU/LiDARの時刻同期・deskewの残差、closed-loop制御自体の影響、backendの因子重み付け設計(未検証)

次のアクション、および検証を進めるかどうかはユーザー判断待ち。
